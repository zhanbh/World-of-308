# 来源、原结果与流水保留方案 v1

日期：2026-10-21。E06设计候选，未执行清理、迁移或备份；不表示正式eng-review通过。依据[物理映射](asset-physical-mapping-v1.md)及[配置与迁移](configuration-and-migration-v1.md)。

## 1. 首版选择

首版不启用权威去重记录的自动TTL，也不立即引入冷热双存储。operations原结果、来源终态、资产流水及其解释所需配置保留在当前权威存储。先通过分页和索引控制访问，不以清理数据解决列表性能问题。此选择降低首版归档协议复杂度，但存储量会增长；上线前必须给出预期增长、费用监控与容量处置计划，不能据此承诺无限低成本。

未来归档属于独立发布能力：完成下述迁移与恢复证明后才能启用。当前小用例预算不包含未实现的归档服务、冷存储访问或额外目录键，不能把未来能力算作已具备。

## 2. 各类数据的清理边界

| 对象 | 可以移出玩家视图的内容 | 必须保留的权威事实 |
| --- | --- | --- |
| 已领取或过期邮件 | 正文和展示附件详情，遵守既定删除/过期规则 | 同键source stub、归属、来源、原截止、各附件发出量/实领量、终止状态、结果摘要；固定结果若仍被未决操作引用则不可删除 |
| 永久待领 | 已交付项从待领列表移除 | grant交付终态、itemId及来源；未领实例与grant永不因列表过大过期 |
| 关闭场景的地面掉落 | 从场景查询排除 | room来源及已领/失效状态、终局引用；首版保留room记录，不把普通掉落补成待领 |
| 售出或损毁装备 | 从可用装备查询排除 | itemId、生成来源、退役原因/操作、必要历史属性；不得释放旧itemId重新造物 |
| operations | 无需出现在普通玩家列表 | 请求类型/摘要、授权归属、原决定及可恢复的原结果；不能只留“已处理”而丢失玩家查询结果 |
| assetJournals | 不进入在线列表，可分页审计 | 数量输入输出、追踪头、版本变化、来源/配置及原操作引用；仍有后代追踪头引用时不删除祖先 |
| 挑战、会话与配置 | 关闭后从当前状态查询排除 | 来源去重、终局、撤销/代次与解释历史结果所需版本；当前账号会话栅栏始终保留 |
| 调试日志 | 按单独运维策略清理 | 不以调试日志充当唯一账本或补发依据；日志清理不级联资产集合 |

邮件30天仍是玩法时效，不是来源凭据保留30天。账号/角色删除、角色名释放等尚无已确认玩法，不在本方案添加自动删除规则。

## 3. 将来归档时的最小协议

归档必须保留原热键的终止凭据，不能删除后把“不存在”解释成新意图。候选热键stub含owner、schemaVersion、原请求摘要或业务sourceKey、terminalStatus、archiveRef、payloadHash、archiveGeneration；不另建一个容易漏查的平行去重目录。完整原结果、流水及配置依赖可以搬迁，摘要不能替代其可恢复性。

迁移顺序：选择已终止且无在途写的候选 → 固定内容与版本 → 复制不可变归档 → 校验长度/摘要及依赖闭包并试读 → 事务CAS原热键为stub → 保留原副本至恢复验证完成。复制成功但CAS失败只产生待清理孤立副本，不能覆盖新数据；CAS成功但响应丢失按原键重查，不创建第二份业务来源。禁止先删除热数据再上传归档。

同键旧请求的处理：先验证当前身份/会话写资格，再查原键；摘要不同仍拒绝；stub命中则恢复并返回原结果，绝不重新执行业务。归档暂时不可用返回可重试的查询不可用/结果未知状态，不能返回确定未执行、重新扣费或自动补偿。未查到热键也不能通过扫描冷存储猜测新旧状态：任何合法归档都必须留热stub。

source stub与operation stub作用不同：换operationId仍须查业务来源，不能重新领礼包；同operationId则返回原交付量。合法部分领取按来源版本和实领区间继续，不能因保留旧领取回执而封死剩余附件。

首次会话建立的确定键凭据同样保留，不因普通operations尚未建立而漏掉登录响应丢失场景。当前会话授权先于历史结果读取，归档回执不恢复已撤销会话的写权限。

## 4. 恢复与归档不能相互替代

备份恢复需同时覆盖资产、来源、operations、流水、会话栅栏及配置引用。只恢复钱包/背包而遗漏后续已提交来源会导致复制资产；只恢复来源而漏资产则可能吞奖。恢复点之后的合法提交必须有可重建证据，否则进入维护隔离与逐项核对，不能直接开放写入后让客户端试着重放。

恢复演练须证明：同一资产快照与凭据覆盖一致；服务端新会话代次使恢复前旧写失效；已确认收益不被自动重抽/重发；追踪链和归档引用可解析。实际RPO/RTO、备份周期、恢复点后日志覆盖能力取决于目标平台，当前不虚构保证，也不承诺仅靠应用账本就可找回丢失的整笔提交。

归档访问须按账号归属裁剪，不把归档URL或管理员读取凭据返回客户端。断开归档、校验失败和缺失依赖应留下可定位的运维事件；修复使用独立稳定修复来源与审批记录，不篡改原operation含义。

## 5. 实施后的验收矩阵

| 故障/重试 | 必须观察到的结果 |
| --- | --- |
| 删除过期邮件后再次触发同等级奖励 | 不重发，保留原过期结果 |
| 部分领取成功但响应丢失 | 旧操作返回原数量，新操作只能领取剩余量 |
| 复制归档后进程退出、CAS尚未成功 | 热记录仍权威，业务不重复执行 |
| CAS成功但迁移响应丢失 | 同热键stub可恢复原结果，重复归档不改变来源 |
| 归档读取超时或摘要不符 | 不宣称未执行、不重复扣费/补奖，转恢复处理 |
| 100格多次拆分/合并后的祖先归档 | 可解析全部数量流，不要求在线整理遍历祖先 |
| 恢复后旧会话发迟到请求 | 旧代次拒绝，合法已提交原结果仍能安全查询 |

这是待实现的验收要求，不是已通过的故障测试。首版保留策略已给出，增长预算、平台备份能力及正式运维指标仍开放；未来启用物理归档须重新核算读写/查询费用并审查协议，不默认随业务编码一并上线。
