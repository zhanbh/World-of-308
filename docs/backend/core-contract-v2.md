# S01–S04 核心契约 v2（工程设计，待实施）

更新：2026-10-20。依据：[规格](../spec.md)、[挑战流程](../challenge-flow.md)、[D06切分](../design/implementation-slices-v1.md)、[UI验收](../design/town-interactions-acceptance-v1.md)。
本文是下一轮实现的契约提案，不是已发布API；不修改当前TypeScript代码或数据库。v2规则优先于v1文档中冲突部分，其余会话栅栏、截止检查、持久去重和事务约束继续适用。字段名和命令名为工程候选，UI不得据此假设接口已经可调用。

## 1. S01：版本与请求结果

### 1.1 三种版本分开

| 版本 | 用途 | 规则 |
| --- | --- | --- |
| protocolVersion | 命令/视图形状 | v2为目标，旧客户端不静默套用新资产操作 |
| schemaVersion | 持久数据结构 | 每类聚合有转换器；不可只改数字而不迁移字段 |
| configVersion及子配置引用 | 玩法与测试数值 | 已发布版本不可原地改写，客户端不能自选更有利版本 |
| aggregate version | 钱包/容器/角色/挑战等并发控制 | 单调递增；不是协议或配置版本 |

配置发布清单区分test-only与可发布配置。职业、技能、装备、初始化邮件、容器解锁、商品价格、怪物/副本、时间窗和策略引用须可校验。价格/伤害未定时只使用显式测试配置；缺配置返回CONFIG_NOT_READY，不回落硬编码价格。物理表和SDK配置后续适配，不在文档中声明已建集合。

### 1.2 命令信封与结果

沿用command、operationId、expected、payload与受信传输身份；目标protocolVersion为2。expected按实际受影响的角色、物品、容器、钱包等对象标识与版本校验，不能只用一个containerVersion代表两个容器。返回serverTime、operationId、replayed及committed/rejected/unknown。

- committed：附带原业务结果及受影响对象版本，不伪装为当前全量资产。
- rejected：稳定业务原因；资产意图未执行，但先处理的到期挑战转移可能已提交，应返回或刷新相应状态。
- unknown：不能推断扣费是否发生。客户端查询原操作，不新建另一笔意图。
- 同账号同operationId同命令/参数/原expected摘要：当前合法会话下返回原结果，先查去重再检查过期expected；不同摘要返回OPERATION_MISMATCH。
- 版本冲突后要换数量、物品或付款方式属于新意图，读取最新状态再用新ID。未知提交不能靠改参数重试。
- 原会话失效后不能重放其写请求；新会话可授权查询本账号原操作结果，展示原结果后再读取当前状态。
- 查询notFound不能证明在途请求绝不会提交；查询后仍可用原ID和原参数重试，由唯一操作键保证只执行一次。拒绝再发新意图前必须排除原意图的在途副作用。

不提供setBalance、saveInventory或客户端整包覆盖存档命令。空列表、可重试网络问题、业务拒绝和结果未知应区分，不能全归为失败。

### 1.3 配置与随机结果

挑战绑定入场内容配置；服务操作绑定当次报价及相应配置引用，所有随机生成来源持久化。事务回调自动重试不重抽奖励；不同调用竞争同业务来源只采用首个成功结果。掉落策略等挑战配置已确认在新挑战生效，当前挑战沿入场版本，不假定新策略会重抽旧奖励。

## 2. S02：三类容器与物品位置

### 2.1 容器视图

| kind候选 | 所有者 | 容量与权限 |
| --- | --- | --- |
| backpack | accountId+characterId | 20起，金币4档至100；可穿戴/消耗的库存来源 |
| personalVault | accountId+characterId | 20起、4次各20至100；金币/点券二选一解锁；允许本角色绑定物品 |
| accountVault | accountId | 100全部开放、不扩容；允许未绑定/账号绑定，禁止角色绑定 |

视图含containerId、kind、capacity、unlockStage、slots、version、allowedActions；个人/背包所有者由服务端解析校验，不接受客户端伪造账号归属。账号金库使用显式kind，不能从页签文本推断。金库仅银行可操作，服务位置校验与可信程度需在S09/S10协议适配中明确，不能把客户端“已打开银行”布尔值当安全依据。

个人金库进度不随角色切换共享。解锁事务同时校验当前stage、配置价格、付款币种和钱包；同档并发金币/点券只能成功一次。价格不强制套用背包或兑换比。

### 2.2 物品与位置不变量

装备唯一实例包含绑定类型none/account/character及对应所有者，独立记录合法位置：container、equipped、pendingGrant等；邮件尚未领取的实例/描述由其来源交付状态控制。物品生成、交付与销毁均要可追溯来源，不能复制一个实例到两个位置。

堆叠按模板、绑定种类、绑定归属及会影响使用的实例属性兼容合并，上限20；不同绑定不混堆。存取不改变绑定、强化、耐久或来源。角色绑定装备和道具不能进账号金库，也不能通过个人金库移给别的角色。

拖动只是表达转移意图。候选命令inventory.transfer包含characterId、sourceContainerId、targetContainerId、item/stack标识、quantity及相关expected版本；目标槽是否必须指定在实现中按已定拖动体验细化，不先新增整理/交换玩法。空间不足整笔拒绝，返回可容纳数量供玩家调整；不自动转移一部分。

校验顺序：身份/会话→原请求去重→容器与物品归属→版本/数量/绑定→目标容量→一致提交。两容器、实例位置、资产流水和操作结果原子变化。双方均有空余但同件物并发转移时，也必须仅一笔成功。

### 2.3 原子范围与账本

每笔资产写均参加账号writeRevision栅栏，涉及的实例、堆叠、容器、钱包、业务来源和operations一起提交。流水记录delta/move、前后版本、来源及报价配置，不拿流水代替实际余额。

扩容、银行存取、买卖、修理、强化和领取都禁止半提交；一键邮件领取是多个附件业务单位的有界编排，允许部分成功但必须给每个附件稳定交付来源，不能把它误称为整封邮件一次原子成功。

## 3. S03：角色初始化、邮箱与永久待领

### 3.1 创角一次性初始化

character.create按account+class占位，支持warrior/hunter，每职业一个。事务/等价安全交付方案需同时保证角色、20格背包、20格个人金库、初始穿戴白武器来源和新手邮件来源一致，账号100格金库与共享钱包按账号生命周期创建，不随第二角色重置。

新手邮件角色绑定8血药、8蓝药、10纹章；初始金币/点券不赠送。业务唯一键按角色+礼包节点，客户端operationId之外另有来源去重，不能换请求ID再次领。

等级5/10/15/20/25/30固定绿武器邮件，装等15/20/25/30/30/30；升级跨节点每节点一次。初始和邮件模板须明确职业/绑定/品质/耐久等字段，不能以测试直接塞包替代正式发放。

### 3.2 邮件与待领的独立生命周期

一键邮件领取遇到装不下的附件跳过并继续后项，最终汇总；不是遇到第一项满包就停止。每次部分交付保留本次操作与附件版本，同批次重放返回原结果；新意图才可继续处理余量。

| 对象 | 所有权与时间 | 交付 |
| --- | --- | --- |
| mail | 角色；createdAt、expiresAt=30天、状态 | 附件逐项或一键尽可能领取；未领附件不能手删，过期删除且不补发 |
| pendingGrant | 原奖励角色；createdAt、deliveryState | 不过期、不因数量硬限拒奖；入原角色背包，不能直接穿戴/出售/转角色 |

共用UI不合并数据、TTL或权限。列表按(createdAt DESC, stableId DESC)游标，stableId只解决相同时间稳定排序；每页数量有上限但具体UI条数待设计。领取重试不修改原createdAt，刷新后不跳到列表头。

命令/查询候选：mail.list、mail.claimAttachment、mail.delete、reward.list、reward.claim、character.get、inventory.get。附件只提交标识与数量/版本，不提交自报奖励描述。对已过期邮件先落实过期再拒领，不能用客户端旧时间领取。

一键领取以服务端裁剪后的批次执行，返回逐项结果及剩余；每个附件交付有稳定来源和原结果。整组不是无限大事务；堆叠附件已确认可按背包可容纳数量部分领取，剩余保留，装备整件领取。每次部分交付用独立意图和附件版本去重，同一旧请求不再扣剩余数量；不同新意图可继续领取。

永久待领同原角色实例或来源领取，pending→delivered和入包原子进行，满包不清待领。地面掉落满包仍留地，不自动进永久待领；通关专属装备按正式规则独立交付。

## 4. S04：体力快照、场景与终态

### 4.1 候选字段

角色保留stamina.value、refillWindow；挑战新增staminaSnapshot{entryValue, remaining, entryRefillWindow, entryAt, version}，以及staminaSettlement{state, settledAt?, loadedRefillWindow?}；角色/账号保留指向该有效挑战的权威关系。房间含nominalCost、paidCost、paymentState、paidAt，不用paidCost>0来判断是否已处理。

不必逐帧写体力，逐房实际扣费/零扣费与room manifest共同持久化。所有字段与结算受服务端时钟、会话栅栏和版本保护，不只是UI显示快照。

### 4.2 入场与逐房

1. 确认创建挑战前，在城镇按服务端时间落实角色应有的最近固定补满，余额至少1；等级/难度/在线/可用武器等检查沿规格。
2. 创建挑战锁体力快照和账号唯一挑战指针；仅浏览难度页不扣费。保持现有start与enterRoom分离：start锁快照，首房进入时才扣第一房，不额外新增入场费。
3. 新房实际扣费=min(remaining, nominalCost)，普通nominalCost=1，特殊=3；remaining最低0，0时仍记录零扣费并允许合法推进。
4. 本局所有状态读取/同进程恢复使用该remaining。固定补满时间不写入挑战快照，后续房间不能从最新角色余额继续扣。
5. 同(challengeId, roomNo)不同operationId也最多处理一次；已处理的零扣费房间同样不可再扣。

### 4.3 回城加载与固定窗口

工程建议将本局remaining作为出场余额基底，在结算回城事务中按最新窗口计算：

- 若回城时仍为entryRefillWindow，角色余额取本局remaining。
- 若已经跨过入场窗口，则按已定固定补满加载308，之后新挑战才从它创建新快照；旧房间不得倒扣刷新后的余额。
- 结算用challengeId作唯一来源，迟到/重复结算不可覆盖角色后续新挑战已消耗的余额；判断已结算先返回原结果，展示当前值须另查最新角色状态。
- 如从失败、放弃、超时、重登、接管等多条路径结束，同一挑战只进行一次结束结算，结果终态与体力落账不可分离。不以离线时不在城镇为由丢弃已到的补满窗口。

这解释已确认例子：1点进本→扣0→跨固定补满→击败Boss且仍在副本显示0→回城才加载308；未跨窗口回城仍0。已通关尚在拾取场景不提前当回城加载。以上字段/原子方案为候选，必须用受控Clock验证后实现，不宣称现代码已满足。

### 4.4 场景、死亡和冷却

| 事件 | 挑战与位置 | 体力/冷却 |
| --- | --- | --- |
| 同进程短暂重连 | 合法恢复原挑战，不回旅店 | 继续快照和已处理房间；冷却不重置 |
| 死亡窗口内手动复活 | 原挑战，扣纹章/次数原子变化 | 职业CD清零，药品/饰品不清；满HP/MP与2秒保护沿规格 |
| 首领残留击杀通关免费复活 | completed，保留在线拾取 | 不扣纹章/次数，冷却按既定免费复活矩阵 |
| 在线离开/失败回城 | 原副本门口，门口范围需离开再走入才重触发 | 一次加载体力；HP/MP满，所有技能/道具CD清零 |
| 关闭重启/新设备接管 | 不跨进程续关；下次上线当前角色旅店 | 先结束旧挑战并结算，再加载最新角色视图，不覆盖已保存资产 |

result(active/completed/failed)、lifeState(alive/dead)、sceneState(combat/looting/closed)继续独立；completed永不降为failed。首领确认通关后末房磨损武器归零仍通关；非末房武器0暂停是单独行动限制，不能直接等同dead或failed。暂停时钟的未定细节留给耐久实现，不暗中免费复活。

死亡10秒、断线/后台恢复10秒、复活保护2秒用不同截止与时间基准；截止以服务端now>=deadline判断。死亡期间合法残留击杀升级不解除dead；通关免费复活等沿挑战流程。此处状态校验不证明客户端击杀真实性，正式经济安全仍需后续验证。

## 5. 只读视图与UI连接

全量目录与状态组合已展开为[API契约v2](api-contract-v2.md)、[状态转换v2](state-transitions-v2.md)；药品/饰品、服务位置等未闭合处有明确标记，不能因本稿出现候选命令名视为接口冻结。

视图要提供动作权限/拒绝原因、对象版本和服务端状态，而不是由UI猜测：

- account/character：当前角色、钱包摘要、穿戴、背包/个人金库容量、场景位置；不向其他账号泄露资产。
- challenge：result/lifeState/sceneState、当前房间、快照余额、截止、已确认事件序号、允许动作及升级/复活指令。
- service：当前服务类型、可操作目标、报价版本/消耗/失败后果；强化不返回可供UI展示的概率字段。
- list：邮件/待领按独立权限与游标分页；空列表不是网络失败。

关闭面板不取消已提交请求。客户端按版本接收结果，旧回包不得覆盖新状态；切换金库页签后，原请求仍按原containerId归属落账，不应用到新页签。纯UI稿可使用模拟视图，正式网络协议尚未实现。
