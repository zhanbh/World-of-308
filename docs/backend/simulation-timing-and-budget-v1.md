# 可验证模拟的时间、确定性与预算基线 v1

日期：2026-10-21。状态：工程候选，待eng-review与独立验证；不改变已确认玩法，不是性能测试结果。依据[输入协议](verified-action-protocol-v1.md)、[事务预算](transaction-budget-worksheet-v1.md)、[挑战生命周期](../challenge-flow.md)。

## 1. 候选参数及选择理由

| 项目 | 候选基线 | 使用限制 |
| --- | --- | --- |
| 判定步长 | 固定10ms，即100逻辑步/秒 | 不是100次网络请求/秒；同刻事件仍按稳定优先级与序号处理 |
| 一般输入发送 | 目标每500ms提交一个有界片段 | 空闲可合并但不可超过已验证跨度；频率与费用实测后调整，不冻结为产品规则 |
| 单段模拟跨度 | 候选最多1秒，最多100步 | 请求大小/动作条数另有上限；恢复积压分段，不在一次请求重放无限历史 |
| 权威检查点 | 每个成功片段原子提交游标与状态 | 不能先确认资产、隔很久再写恢复状态；压缩/归档周期另计 |
| 位置表达 | 候选整数子像素，单位为1/1000设计像素 | 需校验最大坐标、乘积及速度余数，禁止溢出；与渲染坐标转换分离 |
| 动作时间 | 原始配置毫秒或有理数时间，按统一边界规则映射逻辑步 | 急速后的时长不能客户端向下取整、服务端向上取整；不逐段取整后造成总预算漂移 |

10ms候选可表达300ms连招间隙、120ms缓冲等既有时间；急速后不整除的节点需要保留原始时刻或余数，不能因固定步长累积误差改变跳数/伤害预算。所有参数须与实际移动、碰撞及最高急速场景一起验证，失败则调整候选并复审，而非强行迁就数字。

## 2. 时间状态与可接受进度

每个场景保存服务端活动时间锚点、累计已接受模拟时长、连接状态、sceneEpoch及独立timelineEpoch。片段只能连续推进，累计推进不能超出服务端允许的墙钟活动时间预算；禁止每段额外加容差造成无限加速。当前基线候选不确认未来逻辑时刻；如后续引入前沿容差，必须是单次有界且不累加的独立方案，经复核后使用，不默默开放。

同一场景的死亡、恢复、通关等截止按原服务端墙钟定义，不被候选提交频率改写。对外给出暂停/恢复控制事件对应的游标与时间锚点；重放不能越过这些事件。

### 断线与后台的证据边界

客户端onHide或失联并不自带可信发生时刻。服务端需要在首次出现未确认输入/连接证据缺口时限制可推进前沿，恢复协商只从最后确认检查点继续；不接受任意补报“断线期间其实已击杀Boss”。当网络仍正常但故意少发包时，也不能借暂停反复获取额外时间预算。

当前统一候选见[恢复时序第6节](recovery-timeline-proposal-v1.md#6-统一时序候选本轮方案收敛待用户许可后再eng-review)：输入缺口候选2秒、预测上界1秒，静默恢复沿原租约截止，显式暂停固定10秒；恢复重建锚点并用timelineEpoch栅栏旧输入，死亡截止不动。不能把500ms提交等同平台保证的心跳或倒填真实断线时刻。合同已给具体候选，仍待正式eng-review与后续运行验证，不关闭G03。

## 3. 确定性规则合同

- 输入规范化：摇杆量化到版本化整数范围，X走跑/Y固定速度及斜向规则保留；不以网络量化重新引入四向锁定。
- 判定不读取渲染帧、系统随机或客户端墙钟。共享规则接受显式状态、输入、逻辑时间和随机游标；服务端与客户端使用同一规则版本。
- 配置须固定碰撞形状、命中窗口、目标遍历顺序、同刻事件优先级和精度。末次首领击杀先认定通关再应用该房磨损，沿已确认顺序，不因重放切片改变。
- 急速压缩动作、多段与流血时间，不增加固定跳数/预算；攻击端快照与目标护甲/穿透逐跳实时读取保留。
- 统一数值舍入入口、累计余数与最终结算；禁止将JavaScript浮点偶然一致当作跨端确定性证据。位置用整数并不自动解决伤害/方向/碰撞算法的精度问题。
- 攻击、AI、掉落使用分离随机流；战斗重放不得提前消费或暴露资产掉落私有随机状态。种子可见性尚待安全设计。

## 4. 两阶段计算与竞争

事务外从已确认版本做纯重算，事务内重验输入游标、角色代次、场景与截止，再原子提交结果。版本冲突不得重用过期计算；重复原意图返回已提交结果。计算被拒绝不扣资产、不推进游标，不允许客户端直接按预测奖励入包。

当前挑战不允许换装，沿已有生命周期；仍需支持升级、武器破损、消耗品/饰品增益等合法属性变化，不能据此把所有属性锁成整场常量。房间转换、复活与通关是明确事件边界，不可让一个普通片段跨多个未确认房间。

## 5. 成本预算：先给算式，不虚报容量

按候选500ms一次，连续10分钟活动约1200个片段，重试、状态查询和场景操作另加。若每片段各有一笔原子提交，则约1200次业务事务，而非只有房间结算的7次；这不是计费账单或目标平台吞吐保证。

设每片段SDK读/写调用r/w、平均请求字节b、重试倍数a，则10分钟候选负载为约1200×a×r次读、1200×a×w次写、1200×a×b字节上行，再加检查点/响应/日志和奖励交易。费用按最终平台实际计价维度计算，不能用逻辑键数替代SDK调用或读写单位。

必须记录首本含紫名最多7怪、Boss吼叫与残留、最大急速/流血叠加等场景的CPU、状态字节和动作条数；仍需设定流血实例/投射物等合法并发上界，不能为控制成本删掉既定可叠加预算。超出预算先阻止不合法内容发布或调整实现/协议，不能运行时悄悄漏伤害、丢奖励。

若成本不满足，比较更长有界批次、压缩状态、减少冗余物理记录等方案，并复核响应与恢复影响。不能默认降级信客户端HP或只在通关校验；改成先扣后补也不允许。

## 6. 未来验证矩阵（本轮未执行）

| 场景 | 必须得到的结论 |
| --- | --- |
| 30/60/120渲染帧与任意片段切法 | 同输入、同版本最终逻辑状态一致，动作/命中不受渲染分段改变 |
| 急速1倍/2倍与非整除节点 | 固定伤害预算和跳数守恒，时间误差受统一规则约束 |
| 假快进、重复容差、跳序/异参 | 拒绝越界进度，无资产与游标部分提交 |
| 请求丢失、乱序、后台、恢复边缘 | 不补写暂停期战斗、不重置原截止；确认与未确认状态可区分 |
| 药品/复活/升级/破损/终局竞争 | 消费、效果、残留、生命状态与收益保持既定顺序 |
| 高并发与最大内容 | 有实测资源与费用证据，预算留余量，不宣称仅符号估算已通过 |

下一步是断线/后台时序与确定性接口的工程评审，不要求用户审批每个调优小数。新规则选择或独立技术验证代码需明确范围；当前只形成设计材料，仍未安装依赖、跑新模拟或操作云资源。

## 恢复体验最新确认（2026-10-21）

用户明确战斗表现不要求强一致，允许秒级回溯；短恢复先查询原请求结果，再以服务端最新确认检查点恢复，未确认移动/攻击表现允许修正。这不放松钱包、消费、发奖与原操作结果的原子性，已确认资产和收益不撤销。

持续无法恢复时显示「网络中断，请重新进入游戏」，停止继续战斗并要求重新进入；沿用既有10秒恢复窗口，不另增宽限或自动续关。未通关超时失败/关闭并保留已保存收益，已通关仅关闭拾取场景、不撤成功；新launch默认旅店，不重启续关。客户端提示不单独改服务端结果，下一请求/清理仍按原持久截止处理。

此前为减少修正提出的持久输入收据不作为本期必需方案；采用原操作结果和权威检查点恢复。秒级是体验尺度，不保证任何弱网都只退1秒；必须限制未确认预测积压，超上界先暂停等待，不允许无限本地刷怪或离线补报。具体积压上界和时间锚点待工程验证。
