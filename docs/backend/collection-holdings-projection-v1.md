# 缺件检测的同步持有汇总合同 v1

2026-10-22。正式工程评审问题3，用户已选择3A。只补实现合同，不改变缺件策略、检测范围或已生成奖励；无业务代码/索引/云环境操作。

## 资产权威与有界汇总

新增collectionHoldings/H(accountId,scope,characterId或空)，角色与账号共享各一份；字段为owner、revision、domainRef、按collectionKey的permanentCounts与mailLatestExpiryAt。collectionKey=(setId,itemLevel,slotId,可用职业)，只统计当前角色可用的套装部位。当前三类30档套装为11个部位，配置发布限制本期域最多64个collectionKey、每份完整编码≤16KiB；新套装/职业使域超界时先改域与预算，不运行时漏统计或清旧物。

permanentCounts覆盖角色穿戴/背包/个人库/永久待领，账号scope覆盖账号库中合法共享物；其他角色绑定资产不混入当前角色范围。按职业可用性区分；scope仅按实际位置/来源所属决定，只有账号库中的物品进入账号共享汇总。角色背包/穿戴/个人库/待领/有效邮件即使未绑定或账号绑定，也只计其所属角色；绑定与职业仅决定资格，不扩大共享范围（用户批准11A）。缺件判断为角色永久数+可用共享数>0，或角色该key的mailLatestExpiryAt>业务判定时刻。耐久0仍是已持有，损毁/出售移出持有；未拾取地面不算持有。

这份汇总不是第二份可领资产。完整实例/容器/来源仍授权移动与交付；只有资产应用事务可更新汇总，和A栅栏/O/J及原变动同笔提交。缺件奖励只读两份有界汇总，不能信异步缓存，也不遍历历史邮件/grant。来源生成后进入pending即计入，pending领取进包不再加一次。批次内暂占在同一决定的本地差额中体现。

## 变动矩阵

| 变动 | 汇总差额 |
| --- | --- |
| 新套装拾取/直接通关入包/生成永久待领 | 所属角色permanent+1，同笔物化/来源 |
| 同角色穿戴↔背包↔个人库↔待领 | 总持有不变，仍验证位置/来源，不能迁移就重复增加 |
| 角色范围↔账号库 | 原scope−1、目标scope+1；绑定/职业资格按既定限制，数量不能负 |
| 出售/永久损毁 | 原scope−1；耐久磨损/修理与强化未损毁不改持有 |
| 有效装备邮件生成/领取 | 同笔更新邮件贡献与mailLatestExpiryAt；领取时转成permanent+1并移除原邮件贡献 |
| 邮件自然过期 | 用max有效期与now比较即可排除，无需等清理任务改计数 |
| 新账号/角色初始化 | 同笔创建零汇总；初始白/节点绿武器不属于套装，不增加套装部位 |

重复原操作不再次改计数。发现缺摘要、负数、domain无法解释时不静默当缺件再补装备；返回配置/完整性不可用并保留原资产，受控核对/重建。已有数据的初始化由真实来源盘点，不猜测或重新赠送。

## 邮件时效：保存最晚到期，不保存会过时的有效邮件总数

新增mailHoldingContributions/H(mailId,attachmentOrdinal)：accountId/characterId、collectionKey、expiresAt、mail/attachment引用、active及sourceRevision（≤1KiB）。这是内部索引贡献，不是余额；邮件产生/领取与该行及角色汇总同笔。保留原邮件到期时间，不因领取、重试或重建刷新30天。

一个key只要存在未领且未过期装备就算已持有，因此汇总保存active贡献的最大expiresAt即可；now达到该值时该key全部邮件贡献均过期，无后台准时任务依赖。过期来源stub和贡献保留审计，不能借保留记录把过期物算已持有。

移除当前最大期限贡献时，下一候选最大值通过内部索引(accountId,characterId,collectionKey,active,expiresAt DESC,contributionId ASC)在事务外准备。当前单项装备领取只移除1条，最多取前2条、排除该条即可获得下一最大；批领每子项独立处理，禁止一次删除无界贡献。邮件过期不需要逐条删除；手动删邮件已要求无未领附件，不产生隐藏的多附件移除路径。

预读取A.writeRevision→取有界候选→资产事务重验同一A版本、邮件/贡献/汇总版本→原子消费并写新最大值。所有相关写入均串行修改A，避免候选期间新增/领取改变结果；候选冲突重算，不用旧查询填最大值。索引查询须提供适配器已验证的一致性；若SDK不能保证查询相对该写栅栏的可见性，则该邮件贡献方案不能启用，必须返回设计调整，不能退回盲猜。此项列为接入验证依赖，不冒称平台已证明。

本期没有活动装备邮件，既有初始化/等级邮件为消耗品或绿武器，但合同仍支持将来合法套装附件；新增发信来源上线前必须验证上述过期/移除最大值路径。角色绑定/品质/装等/套装资格在生成贡献时验证，不能由客户端设置collectionKey。

## 联合事务预算

通关抽套装需读角色+账号两份汇总，新增奖励只写角色汇总：在原最坏R43/W33上追加R2/W1，成为R45/W34，共79次单键读写设计量。即使选择的已有部位仍更新计数，不因“已持有”丢后续数量信息。CP按需分块已批准，实际常态仍按u/d计量；**原R43/W33不再是含缺件检测的完整最坏预算**。

79紧邻候选80调用目标，仅是设计量，真实SDK额外调用/commit/retry未证实；不据此宣布通过。汇总每份≤16KiB，终局额外最多16KiB写，其他对象预算需计入；现有1.5MiB总写预算尚有纸面余量，真实编码仍待测。

银行跨scope套装转移额外读写2份汇总；同scope换装不必重写；套装出售/损毁额外读写1份；非套装不走此路径。单套装邮件领取额外角色汇总+贡献行各1读1写，事务外索引最多2条另计查询/费用。账号/角色创建各增加本scope零汇总1读1写；不把贡献索引查询藏进SDK事务操作小计。维护/重建用例必须单列预算与版本竞争，不能假设它们免费。
