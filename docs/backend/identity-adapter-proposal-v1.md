# 身份适配与首次会话建立候选 v1

日期：2026-10-21。设计候选；未安装SDK、创建AppID/环境、部署或登录实测。正式eng-review须用户确认后启动。

## 1. 平台证据与选择边界

CloudBase官方[小程序云函数接入](https://docs.cloudbase.net/en/recipes/add-cloud-function-wechat-miniprogram)描述wx.cloud.callFunction与wx-server-sdk上下文链路，并明确与Web SDK自定义登录不同；[普通云函数调用](https://docs.cloudbase.net/cloud-function/how-use)区分小程序、Web、服务端与HTTP入口。这些是小程序资料，不直接证明Cocos微信小游戏产物采用同一接口即可安全运行。

本轮尝试读取微信小游戏wx.login、auth.code2Session及云开发初始化官方页面，均未取得正文。故当前不将任一具体链路标为已验证，也不依据搜索摘要补出凭证时效。候选优先验证小游戏原生可信云调用；不支持时再完整评估登录code交换及业务令牌方案，不能在同一入口自动降级到接受自报openid。H5动作原型仍是本地验证入口，不因此开放正式账号/资产接入。

## 2. 核心只接受可信身份对象

Adapter输出VerifiedIdentity{provider,appId,subject,environment,invocationKind,verificationMethod}，其中字段全部来自已验证平台上下文或完成验证的服务端凭证交换；请求体不能构造此对象。内部identityLinks按provider+appId+subject确定键映射账号，环境隔离纳入部署命名空间，不拿UnionID缺失当登录失败，也不擅自跨AppID合并账号。

当前API中的accountId/characterId用于目标引用和归属校验，不用于证明调用者身份。业务核心不接触session_key/AppSecret；SDK连接可以复用，VerifiedIdentity和请求可变状态必须每次重新建立。调用来源不在白名单、AppID不符、上下文缺失、凭证验证失败均在资产事务之前拒绝。

玩家入口与定时任务、迁移、管理员入口分离。内部任务使用独立服务身份及稳定systemSourceId，不伪造玩家上下文。HTTP若未完成独立身份方案则关闭，不能因为服务端SDK可访问数据库便认为HTTP调用者可信。

## 3. 首次open的物理防重

选择独立sessionOpenReceipts/H(identityKey,launchId,openOperationId)，覆盖普通session/operations建立之前的重试。记录身份引用、请求摘要、launchIdHash、结果sessionId/epoch、提交时间和有界原结果；不保存平台秘密。此键不包含配置版本，不自动TTL。首次open的预算独立计算，不能套用普通资产Rbase/Wbase。

首次创建账号在同一事务内检查并创建identityLink、account、共享钱包、账号金库、session和openReceipt；具体候选账号ID须在事务重试中稳定，竞争identityLink失败后重读胜出账号，不生成第二账号。新手角色资产在创角流程创建，不在重复open时再次赠送。已有账号open则读取同一账号栅栏与当前会话，原子提交代次切换和回执。

同open键异参拒绝；同键同参且仍为当前会话返回原结果，不再次递增epoch。原回执对应会话已经被新会话替代时，只可返回历史提交状态及“已被替代”，不能把历史结果描述为当前有效登录。响应丢失重试沿同键查询，不能每次生成新的launchId/openOperationId。

旧launch已有撤销记录时不得重新open抢占。随机launchId或客户端时间不能证明哪次启动更新；本轮选择第6节的prepare/commit握手及epoch比较交换，处理已观察请求的竞争和退出进程的迟到首包。不声称跨设备物理启动时间可由该协议证明；小游戏平台链路及验收未通过前不关闭C01会话门禁。

## 4. 登录失败与资产请求失败分开

| 情况 | 处理 |
| --- | --- |
| 尚未取得可信身份 | 登录失败，不创建账号/钱包；不给匿名身份正式资产权限 |
| 已取得身份，open提交结果未知 | 以原open键查回执；不得重复初始化或猜测失败后补发 |
| 当前业务会话过期/被替代 | 拒绝写，重新走合法登录；不借旧操作成功回执恢复写权 |
| 平台凭证需刷新 | 由已验证Adapter流程处理，不改变已提交资产结果；具体刷新周期待官方核验 |
| 战斗短断线 | 沿既有10秒恢复和timelineEpoch规则；平台认证刷新不自动延长死亡/恢复截止 |
| 登录过程发现旧挑战需结算 | 按已定挑战状态和结算协议执行，不能认证成功后先清旧挑战再尽力补资产；联合写集仍需预算 |

玩家可见错误只表达登录失败、会话失效或结果查询中等状态，不泄露平台标识、凭证与内部权限详情。精确错误码与API现有枚举合并时统一，不在此另造相同含义的平行错误体系。

## 5. 实施前待取得证据

- 精确客户端/服务端SDK与runtime兼容性、密钥注入和撤销/刷新能力；不只选择latest。
- 同身份首次并发登录只创建一个账号；open响应丢失重试不重复切代；旧会话/跨AppID/缺上下文/伪造请求体均拒绝。
- 已知旧launch与从未观察的延迟旧首包分别测试；首次open与旧挑战终局并发保持原子及预算约束。

## 6. 选择两步握手，不按客户端时间抢占

C01分为session.prepare与session.commit。prepare只产生短期、绑定可信身份和launch的登录票据，不切换当前会话、不结束挑战、不创建钱包/金库。客户端收到票据后，确认仍是当前启动流程，再commit。只有commit能够在事务内建立/替换业务会话。正常登录增加一次往返，避免一个已退出进程的迟到首包直接踢掉当前玩家。

票据候选loginAttempts/H(identityKey,launchId,prepareOperationId)，字段为intentHash、identityKey、launchIdHash、baseAccountId或空、baseSessionEpoch（未建号为0）、issuedAt、expiresAt、status及committedOpenRef。prepare响应丢失沿同键重试返回同票据；不得重试就延长expiresAt。有效期候选60秒，按服务端时间检查now>=expiresAt即失效；这是工程参数而非新增战斗时限，尚未实测。票据ID不是独立身份凭证，每次仍要求可信平台身份。

prepare在一致读取账号映射与当前epoch后创建票据；不要求锁住账号直到用户完成commit。commit同时校验票据未用/未过期、身份和launch一致、当前账号映射及epoch仍等于base，再原子提交票据消耗、sessionOpenReceipt、新session、账号栅栏及必要初始化/旧挑战处理。账号此前不存在时，必须再次检查identityLink不存在；竞争者已创建则拒绝旧票据，不“顺手登录”到胜出账号。完整物理键集合与旧挑战结算另计预算，不套普通资产命令小计。

票据因epoch冲突失效后，客户端不自动无限prepare/commit抢占；提示本次登录已被其他登录替代，由用户重新进入触发新流程。重复commit先查询同openReceipt；已提交返回原结果，已被替代返回历史状态，不再次切代。commit结果未知时不换票据另开登录，先查原回执；查询不存在仍不证明在途commit不会提交。

客户端每个进程维护一个当前登录流程标识；关闭/替换流程后忽略旧异步回调，不发送其commit。此标识只约束正常客户端行为，不作为服务器身份或跨设备顺序证明。已退出进程没有机会收到迟到prepare响应并发送第二步，故该首包只会产生票据，不会切会话。

| 竞争时序 | 结果 |
| --- | --- |
| 旧prepare先取得epoch=4，新登录commit把epoch改为5，旧commit才到 | epoch比较失败，当前会话不变 |
| 新登录已成功，已关闭旧进程的prepare才到 | 仅创建epoch=5票据，无旧进程commit，不切会话 |
| 两张票据都基于epoch=4同时commit | 共享账号键/identityLink竞争只允许一笔成功，另一笔不自动抢回 |
| commit成功但响应丢失后重试 | 返回同一openReceipt，不再次增epoch或初始化 |
| 旧commit先成功、新commit后到且基于同一旧epoch | 新commit冲突；服务器无法知道用户物理启动先后，不冒充“后启动必胜” |

明确限制：若旧进程仍活着并在新登录之后主动取得新票据再commit，它与用户主动再次登录在身份上无法区分；同身份跨设备也不能凭客户端时钟判物理先后。本方案承诺按服务端票据基础版本原子竞争、防重和拒绝过时提交，**不承诺物理启动顺序全局单调**。如将来要求指定设备绝对优先，需要另行产品规则；本期不额外加入设备绑定、短信确认或账号锁定。

票据到期可以从待登录视图排除，但首版保留确定键及终态，不因删除已用票据允许旧prepare变成新票据。既有10秒战斗恢复不走新登录抢占，不被60秒票据时限延长。上述票据机制为平台无关业务协议候选，具体适配及真实网络乱序测试仍待实施。

## 7. 事务键与旧挑战交接

以下统计唯一物理键，不代表SDK调用次数。L=identityLink，A=account，T=loginAttempt，O=openReceipt，S=新session，S旧=原当前session，W=共享钱包，V=账号库，J=资产流水，K=账号scope零持有汇总（批准3A）。P为必须读取的配置/权限键。新session及候选accountId在同意图重试时稳定；对确定键检查编码原元组，不能依赖哈希碰撞“不太可能”。

| 路径 | 事务读取集合 | 事务写入集合 | 候选预算 |
| --- | --- | --- | --- |
| prepare、未建号 | L不存在、T不存在、候选S | T | R=3，W=1；不提前创建账号，候选S拦截已撤销旧launch |
| prepare、已有账号 | L、A、T不存在、候选S | T | R=4，W=1；读取A版本与T创建在同一事务 |
| 首次commit且无角色/旧会话 | L/A/W/V/S/O/J/K不存在、T | L/A/W/V/S/O/J/K/T | R=9+P，W=9；账号初始化含J及批准3A零持有汇总 |
| 已有账号commit、无角色/旧场景且有当前会话 | L/A/T/O/S/S旧 | A/T/O/S/S旧 | R=6+P，W=5；不重读或重置钱包/账号库，不强造资产J |

prepare重试先识别同T的原意图，返回原base/截止，不拿最新epoch覆盖旧票据。首次commit九键中的A/W/V/S/O/J/K为候选新键，L也必须不存在；T不是不存在键。若首次路径出现L不存在但候选A/W/V/K已存在的异常，拒绝并调查，不能覆盖或“补齐后继续”。已有账号映射缺钱包/库同样不是重复初始化的授权，需要显式修复来源。

2026-10-22 ST01实施核对：历史八键小计是未加持有投影的核心集合，按已批准[持有合同](collection-holdings-projection-v1.md)账号初始化另加K一读一写，成为当前九键；不是新增玩法。为拒绝已观察的旧launch，当前候选session键按身份/launch稳定，prepare额外读同一候选S。实际SDK计数/部署均仍未验证；旧评审快照保留原数字，不回写历史结果。

已有账号、有选中角色但无旧场景时，在普通commit基础上增加当前角色C读写，原子落到该角色隔离旅店并应用既定上线状态/体力加载；若由此引发资产变更，则增加J读写及必要投影键。不得遍历账号全部角色重置其状态。没有当前S旧的已存账号采用显式分支，去掉S旧键，仍校验A所表明的合法状态，不能因客户端没带sessionId就忽略它。

### 带旧场景的commit

先在同一事务读A中的activeChallengeId/openSceneChallengeId，再按确定键读取相应H挑战、CP检查点、所属C角色；两指针同一挑战只读一次。若指向不同挑战或归属不一致，走完整性错误处理，不随机选择一份删除。旧会话有效资产命令也必须写A栅栏，因而与接管事务竞争。

- H仍active：按既有结束来源标记failed/closed，结算一次体力，已保存经验/金币/装备保留；不重放未确认输入，不额外判一次死亡或死亡磨损。
- H已completed但looting：保留completed与通关来源，仅关闭拾取并结算体力；不再生成通关装备/待领，不撤销成功。
- H已closed但A仍有指针：只在版本及归属一致的前提下清理同一旧指针，不把其他新挑战一起关闭；已有staminaSettlement不得再次覆盖C当前值。
- 关闭以H/场景代次为权威，使所有旧地面来源不再可领；不逐个更新历史房间或每件drop。后续地面查询/拾取必须先验H场景仍开放，不能只读room就返回可领取。

会话撤销、新S建立、T消耗、O结果、H/CP关闭、C旅店位置与必要体力结算、A指针及J在同笔提交。J使用稳定openOperationId来源；账号初始化与旧场景交接互斥，不会同一首次commit额外处理旧挑战。按实际集合求并集预算：以上普通已有账号基数R6/W5，加H/CP/C/J四键时为R10+P/W9；若有额外投影或实体必须显式加计。此小计以关闭无需钱包/装备/房间写入为前提，不适用于任何新增补偿、重算伤害或清房奖励方案。

CP必须持久标记该场景不可再接收输入，与H关闭一致；若实际CP物理上内嵌H则合并为一键并重算，不能既按独立键部署又按内嵌计费。超时关闭不应遍历历史rooms，历史来源的审计保留与场景有效性是两个问题。

### 并发的确定结果

旧首领片段先提交时，接管重试看到completed，只关拾取；接管先提交时，旧片段因A会话/场景栅栏冲突拒绝，不接受迟到首领把failed改completed。旧药品消费先提交则保留消费及已确认结果；接管先提交则消费拒绝，不凭客户端动画扣药。旧体力结算先提交时复用其结算凭据；接管不能重复加载覆盖。

commit提交成功后，即使新客户端资源加载失败也不回滚旧场景结算；重试查O，继续显示当前登录结果。T在事务重试期间过期则拒绝且整笔不提交，已经提交但查询时过期的T不影响O成功结果。交易提交未知先查O，不把请求超时直接解释为T未消耗。

仍需平台验证多键快照/CAS冲突、SDK重试及字节；上述是候选物理预算和事件验收设计，不是实测，也未关闭身份适配门禁。
