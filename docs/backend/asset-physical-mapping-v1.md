# 容器、来源与原结果的物理映射候选 v1

日期：2026-10-21。E02/E03方案收敛，待用户确认启动正式eng-review后审查；未建集合、安装SDK或运行平台测试。只选择当前MVP资产布局，不增加交易/回购/分解或新容器玩法。

## 1. 本轮选择

| 物理对象 | 确定键与内容 | 不另建的重复对象 |
| --- | --- | --- |
| containers | H(accountId,kind,characterId或空)；容量/版本、最多100格、堆叠数量与单个追踪头 | 不按格建100个文档，不另建每堆数量余额 |
| equipment | 确定itemId；完整词条/强化/耐久/绑定与唯一归属 | 槽内不复制可变装备属性 |
| rooms | H(challengeId,roomNo)；manifest、击杀来源、有限地面掉落/交付状态 | 普通地面每件不另造grant文档，拾取前不物化完整装备实例 |
| mails | H(characterId,mailSource)；有界附件、固定结果、发出/累计实领/过期凭据 | 不为同一附件再建并行可领取grant余额 |
| rewardGrants | H(奖励来源,ordinal)；永久待领及其交付状态 | 不把所有邮件、即时金币/经验都变成可领取grant |
| operations | H(accountId,operationId)；请求种类/摘要、决定及有界结果/版本引用 | 不存整个背包或完整战斗存档 |
| assetJournals | H(accountId,operationId,asset)；一笔有界资产变更及堆叠谱系凭据 | 不为一次整理的每次两堆合并逐个写流水文档 |

新手/等级邮件的source不含当前配置版本，不能换配置就重新发。以上H是逻辑确定键，具体编码及目标平台长度能力仍属适配验证。

## 2. 容器内位置与装备归属分开

容器slots是容器内格号的唯一权威；装备location存container{containerId}，不再持久复制slotIndex。客户端拖动仍可携带格号提示及容器版本，服务端从当前slots验证itemId的实际位置。装备只能在该容器出现一次；穿戴引用与实例归属同事务维护。

因此仅排序/整理不改装备location或equipment.version，跨容器转移仍同时改两个容器和实例归属。穿戴/卸下仍同时改角色13槽、背包和涉及实例，满包原格交换/卸下需空格规则不变。旧EquipmentLocation.container.slotIndex定义被本候选替换，不能同时保留两套权威位置。

equipment槽可附sortHeader{itemLevel,quality,slotKind}，仅包含生成后不可变的排序事实，由可信物化/移动流程生成并维护；不含强化、耐久、攻强或可变词条副本。整理只验头结构/版本，不声称零实例读取就完整验证所有头与实例的语义一致；该一致性由写入约束和巡检保证，发现缺失/不一致走重建。战斗、穿脱资格、强化和出售授权必须读实例，不能信排序头，不静默用空值改变资产归属。

stack槽为stack{stackId,templateRef,quantity,binding,traceRef}，quantity仍1～20。traceRef仅指向一个已提交流水输出，不是来源数组。快捷位仍绑定模板，不绑定整理后可能变化的stackId。整理仅当前背包，不扫描两金库，不新增银行整理功能。

## 3. 堆叠谱系：有界单笔，不在热路径遍历全历史

assetJournal包含有界输入头、输出头及数量流：

- 新领取：输入为mail/grant/room确定来源、载体版本/实领前后区间及实际交付量；输出指向新/合并堆叠。来源累计实领与数量变更同笔提交，同来源多次合法部分领取不能被误判为重放，也不能重复消费同一实领区间。
- 拆分/合并/跨容器：输入引用参与堆叠的旧traceRef及完整参与数量，输出包含源容器余量和目标堆叠；每个受影响输出获得本流水的稳定ordinal。不能只记录转出量而丢掉余量的来源。
- 消耗/出售：输出含消耗或退役数量，不重新进入可领取来源。金币变化记录同笔。
- 纯排序：只记录有界位置排列/变更，数量和traceRef不改，避免无意义拉长来源链。

按templateRef和binding分池守恒；不跨角色绑定合堆，不将不同来源当可改变绑定的理由。谱系是可审计的数量流，不给同类道具发明逐个不可替换序列号。写入只验证当前容器/来源状态、版本和本笔守恒，不递归读取历史流水；历史追踪在离线审计分页执行。

整理最多处理一个容器100格；单次存取最多涉及两个100格容器。流水把参与记录装入一笔有界文档，不采用“100次合并各写一个新来源节点”的布局。若真实编码超过预算，先调整有界编码或提交完整替代设计，不在运行中部分整理或丢追踪信息。

来源/流水在归档契约确定前不自动TTL；只保存最新头不代表可随意删除祖先流水。压缩/归档须能恢复终止凭据与数量流证明，此生命周期仍需E06闭合。

## 4. 来源按载体定位，互斥交付

SourceLocator候选：roomDrop{roomId,dropId}、mailAttachment{mailId,attachmentId}、grant{grantId}、challengeClear{challengeId,ordinal}。sourceKey是与载体无关的稳定业务键；引用不意味着一定有独立rewardGrants文档。

### 地面与即时收益

rooms.kills/drops保存固定来源和状态，重复击杀/拾取查同一房间来源；即时金币/经验与确认片段原子提交，不增加可领取金币附件。地面满包仍留地。成功拾取装备才按H(sourceKey,ordinal)创建equipment，放入背包并标来源交付；场景关闭后地面来源失效，不变成永久待领。

### 邮件与礼包

每封邮件附件数量由合法模板声明上界。生成随机结果、quantityGranted/quantityClaimed、绑定与时效在mail同一文档。堆叠部分领取只增加实际交付量；装备整件领取时才物化确定itemId，禁止同一附件另开grant再领一遍。

邮件删除/过期后从玩家列表移除，可移除正文，但保留同键最小来源stub：归属、sourceKey、生成/截止状态、附件发出量/实领量及固定结果摘要。无自动TTL，不能因UI邮件消失重新触发礼包。未领取过期部分失效，不补发。永久待领不套30天规则。

### 通关专属奖励与永久待领

challenge的clearReceipt记录唯一通关来源、固定结果及交付路由。能入包时同笔创建实例并入包，无额外可领取grant；满包时同笔创建pending装备实例和rewardGrant，grant只引用itemId，实例location=pending{grantId}。不同时保存一份可变装备payload。

待领取时重验grant+实例+背包，交付后grant保留来源终态。通关来源不能从direct改pending再发一次；物化、指针、交付来源和原结果同事务。强化溢出纪念品走已确认邮件渠道，采用同样mail来源承载，不增加第二份余额。

## 5. 原请求结果与账本

operations保存稳定摘要、成功/明确拒绝、实际数量/固定随机结果或结果引用、resultVersions。以当前账号授权查原结果；同ID异参拒绝。已提交成功不得因当前包满/报价变更被重算成另一结果。

原结果不是当前读模型。整理返回bagRevision、合并数量、排序方向等有界摘要；客户端如需完整视图另读容器，不能把旧请求返回值覆盖新版本。模拟片段的动作/效果结果上界单独收敛，不把普通资产命令的大小预算直接套全部战斗输出。

当前资产写成功路径选择每笔一个assetJournal。明确拒绝不造资产流水；原结果重放不再写流水。原O和J均确定键，创建不存在性检查也纳入下表，避免遗漏账本占位的成本。

若J已存在但O缺失，不能当新意图覆盖流水并再次消费；进入有明确错误结果的恢复/受控修复路径，原资产不二次变更。当前没有自动清理O/J，归档恢复如何重建终止凭据仍由E06设计，不假设此异常已在真实数据发生。

## 6. 物理键预算示例

成功资产变更共同读取A账号、S会话、O原结果、J新流水不存在键，共Rbase=4；写A栅栏、O结果、J流水，共Wbase=3。原结果命中只走授权读取，不机械套成功写路径。P表示额外价格/权限/激活指针等配置读取，不因缓存而隐去必要校验。

| 用例 | 共同骨架外读 | 共同骨架外写 | 唯一逻辑键R/W（含J） |
| --- | --- | --- | --- |
| 背包整理/排序 | 角色1、背包1 | 背包1 | R=6+P，W=4；不读写100实例，不追溯历史来源 |
| 银行单件装备 | 角色1、服务上下文1、两容器2、实例1 | 两容器2、实例1 | R=9+P，W=6 |
| 银行一叠道具 | 角色1、上下文1、两容器2 | 两容器2 | R=8+P，W=5；目标多堆仍在同一容器文档 |
| 单个堆叠附件 | 角色1、上下文1、背包1、邮件1 | 背包1、邮件1 | R=8+P，W=5；不额外读写同附件grant |
| 单个装备附件 | 上行+新实例不存在键1 | 上行+新实例1 | R=9+P，W=6 |
| pending装备领取 | 角色1、上下文1、背包1、grant1、实例1 | 背包1、grant1、实例1 | R=9+P，W=6 |
| 创角 | 名称占位、角色、背包、个人库、白武器、邮件六个不存在键 | 同六键 | R=10+P，W=9；职业占位使用已读A职业映射，账号库/钱包不重置 |
| 当前穿戴全修 | 角色1、上下文1、钱包1、E个实例、额外投影读取Kread | 钱包1、F个实例、必要角色/评分写Kwrite | R=7+E+P+Kread，W=4+F+Kwrite；E≤7、F≤E，投影映射另收敛 |

这是物理候选键并集，不是SDK调用数、云平台限额或实测时延。实体不存在读取、同键读写、回调重试、序列化字节与适配器额外调用必须另记录。单段同时用药/升级/掉落/耐久的终局事务仍需取全部对象并集，不能拿单项小表证明整段通过。

## 7. 字节与实施前验证边界

候选编码目标：内部ID用有界ASCII标识，容器UTF-8序列化不超过64KiB、单笔资产流水不超过128KiB、普通资产操作原结果不超过16KiB。它们是待验证的应用预算，不是数据库允许上限或已证明的最坏大小；最大合法100格及全量参与整理必须能编码，不能为适配预算减掉已确认容量。

正式eng-review前需补实际字段编码/最大ID长度、最大来源/附件/词条条数、价格配置读路径和投影键。实现后的验证包括：100格整理且来源守恒、跨容器并发、部分领取重试、删邮件后礼包不重发、通关满包路由互斥、真实SDK事务/回调/字节与故障注入。

当前选定了资产布局及小用例预算；终局内容上界、谱系归档、具体SDK和排行投影仍开放，不据此关闭G02/G03或开始业务编码。正式eng-review开始前仍须用户确认。

## 8. 首领终局：来源固定后再选择交付位置

终局仍是一次原子提交，不采用先标通关、随后尽力发奖。事务内根据已确认输入重算终局事实，读取当前背包版本，再决定专属装备direct或pending路由；随机结果由既定来源和固定配置产生，不受背包是否已满影响。事务冲突重试可按最新持有与背包重映射尚未提交的装备候选和路由，但基础随机样本固定；已成功提交来源的装备与路由永不重映射（用户批准5A）；一旦提交，clearReceipt中的路由与结果不可改写。未提交的候选结果不对客户端宣称成功。

| 同一终局内的内容 | 唯一载体与写入要求 |
| --- | --- |
| 首领及同房剩怪的派生击杀 | 当前room记录各来源终态；即时金币/经验汇总到钱包/角色，来源不能因汇总丢失 |
| 升级与跨级礼包 | 角色等级/属性同笔更新；每个实际跨越节点对应确定邮件键，检查不存在性，已发节点不再次生成 |
| 地面掉落 | 只更新room内有界描述/来源状态；未拾取装备不提前创建实例，不自动转永久待领 |
| 通关专属装备 | 一个确定itemId；direct写背包+实例，pending写实例+一个grant；两路均写clearReceipt |
| 磨损、免费复活、解锁 | 实际涉及的装备、检查点/角色、挑战和账号状态同笔更新；最后磨损至0不撤销通关 |
| 原结果与审计 | 一个O、一个有界J，保存终局来源/交付引用；不为每个击杀重复创建O/J |

按本候选计算，终局共同骨架外读取检查点、挑战、当前room、角色、钱包、背包六键；另加E个实际参与磨损实例、M个跨级邮件键、一个新通关装备键、pending时一个grant键，以及额外投影键Kread和配置键P。令Q为本次是否新建pending grant（0或1），则候选R=11+E+M+Q+Kread+P。新实例/邮件/grant的不存在读取已经包含，不能漏算。

若上述六个状态对象均实际修改，候选W=10+F+M+Q+Kwrite，其中F≤E是实际改动的磨损实例数；账号解锁写在共同骨架A，不重复计数。Kread/Kwrite只计上述对象之外的投影键。若实际实现引入额外房间、独立来源、额外会话写或其他物理对象，必须重新取并集，本式不自动覆盖。普通首本的怪数只能约束该副本，不代表所有副本的M、room字节和J字节都已证明有界。

因此direct与pending相差一个grant键，不随本次掉落条数逐件增加grant；但房间与流水的序列化体积仍随合法内容增长。下一项需由三个副本与等级奖励合同给出N/D/M及附件上界，再代入此式和实际编码；当前不能据此宣布终局预算通过。
