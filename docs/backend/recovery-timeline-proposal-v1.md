## 1. 分开三种结果

- 已提交：即使响应丢失也查询原结果，不回滚已保存收益、消费或通关。
- 片段级明确拒绝：不产生效果和资产差额，不推进游标；片段内满值用药/CD未到等合法动作未执行，按输入协议仍记录已处理序号，不能混为缺包。
- 尚未确认的客户端预测：不具备资产权威性；用户已确认允许秒级修正，按服务端最后确认状态恢复；不撤已确认资产。

## 2. 建议事件流程

| 事件 | 服务端候选处理 | 禁止 |
| --- | --- | --- |
| 显式suspend到达 | 原子冻结场景输入前沿，记录不可滚动延长的recoveryUntil；保存当时确认游标 | 用客户端自报时间任意倒改资产或已提交进度 |
| 无suspend的连接缺口 | 有效恢复截止沿原leaseUntil；发现缺口时冻结确认前沿，不在租约到期后额外加10秒 | 每个查询/扫描重新给10秒或形成20秒窗口 |
| 重复suspend、旧心跳迟到 | 按原控制序号返回已定状态；不能从recovery自动变connected | 靠持续重发保活旧场景 |
| 相同输入片段晚到 | 先查询原operation，同摘要已提交则返回原结果；新执行必须受场景/游标与截止约束 | 因HTTP晚到就重复发奖，或对已提交结果谎称未执行 |
| resume到达 | 授权、先恢复未决请求结果、核对所有独立截止，再准备绑定确认前沿的恢复票据并保持recovery；完整视图/资源就绪后scene.ready才CAS切connected及建立新锚点 | 默认沿客户端预测继续或重置死亡截止 |
| 新launch/切角色/接管 | 沿既定结束旧场景/角色代次规则，不当短恢复 | 用恢复票据让新设备续关 |
| 到期查询或后台清理 | 事务内重读截止/状态后按active失败、completed仅关闭处理 | 清理先删来源，或将completed改failed |

服务端接受显式暂停前若无可验证的最后片段，不凭客户端时间承认该片段。存在在途事务时，通过相同场景版本串行决定：片段已提交先保留后冻结；暂停先提交则旧版本新写拒绝。处理时间晚不等于事件可越过已关闭场景。

## 3. 截止竞争

恢复必须同时早于recoveryUntil和适用deathDeadline；采用严格小于，恰到边界按已到期处理作为工程候选。无后台进程准时运行时，下一请求仍根据保存的截止判断，而不是以扫描执行时刻延期。死亡4秒后暂停，再过6秒死亡窗口已到，不因恢复又给10秒。

死亡发生在重算片段内部时，不能按片段处理完成时刻重新给完整死亡窗口；需要把模拟事件映射至受服务端约束的活动时间锚点。映射、网络延迟容差与死亡/通关同刻优先级必须在完整时序评审冻结；不得为便于实现偷延截止。本段尚无验证证据。

## 4. 预测修正提案（后续确认允许秒级回溯，见文末）

短恢复时先查所有在途原请求，以服务端最新确认检查点恢复；丢弃无法验证且尚未确认的最后一小段移动/攻击表现，不补报暂停期间操作。已确认金币、掉落、消费、生死及通关绝不撤销。客户端清楚显示“正在恢复战斗状态”，不要先显示旧预测资产再消失。

这不是承诺只修正500ms：一般发送间隔只是目标，弱网积压可能更长。客户端待确认进度窗口需要有明确上界，超界应暂停预测并等待恢复，避免玩家打很久后才发现都未确认。窗口数值、是否提前显示弱网提示与可接受体验须另做延迟验证。

## 恢复体验最新确认（2026-10-21）

用户明确战斗表现不要求强一致，允许秒级回溯；短恢复先查询原请求结果，再以服务端最新确认检查点恢复，未确认移动/攻击表现允许修正。这不放松钱包、消费、发奖与原操作结果的原子性，已确认资产和收益不撤销。

持续无法恢复时显示「网络中断，请重新进入游戏」，停止继续战斗并要求重新进入；沿用既有10秒恢复窗口，不另增宽限或自动续关。未通关超时失败/关闭并保留已保存收益，已通关仅关闭拾取场景、不撤成功；新launch默认旅店，不重启续关。客户端提示不单独改服务端结果，下一请求/清理仍按原持久截止处理。

此前为减少修正提出的持久输入收据不作为本期必需方案；采用原操作结果和权威检查点恢复。秒级是体验尺度，不保证任何弱网都只退1秒；必须限制未确认预测积压，超上界先暂停等待，不允许无限本地刷怪或离线补报。具体积压上界和时间锚点待工程验证。

## 6. 统一时序候选（本轮方案收敛，待用户许可后再eng-review）

### 6.1 时间与版本的唯一含义

| 项目 | 责任与语义 |
| --- | --- |
| acceptedTick/acceptedSeq | 最后一次原子提交的模拟/输入前沿；恢复不清零，不从客户端预测覆盖 |
| anchorWallAt/anchorTick | 当前时间段的服务端墙钟/逻辑刻锚点；同段内事件墙钟=anchorWallAt+(eventTick−anchorTick)×stepMs |
| timelineEpoch | 绑定当前时间锚点的输入代次；resume成功后递增，拦截旧时钟下的迟到输入 |
| sceneEpoch | 原房间/场景的有效性；短恢复不改变，不误使地面掉落失效。与timelineEpoch不是同一字段 |
| lease.lastEvidenceAt/leaseUntil | 最后一次新有效连接证据及其10秒租约；新输入提交或新序号心跳可更新，旧operation/旧心跳重放不续期 |
| lastAcceptedInputAt | 最近新输入片段的服务端提交时刻；仅新合法输入更新，ready/心跳不伪造此事实 |
| inputGapBaseAt | 当前活动时间段的缺口基点；首次ready设为serverNow，其后新输入提交更新；重放、心跳不更新 |
| recoveryUntil | 显式暂停时固定为服务端接受暂停时刻+10秒；静默缺口沿原leaseUntil，不再加10秒；进入recovery后不可滚动延长 |
| deathOccurredAt/deathDeadline | 首次确认该deathIndex时，将死亡节点映射到所属时间段，再固定+10秒；绝不按响应或resume时刻重设 |

上述为逻辑字段，物理合并在E02/E03选择；检查点不另存可独立更改的死亡/恢复截止，只引用挑战权威。每次处理先验证身份/代次，再落实已有截止，再决定是否更新连接证据；新心跳不能救活已到期场景。

### 6.2 输入前沿与候选工程阈值

沿已有10ms逻辑步、目标500ms提交、单段最多1秒候选。增加连续输入缺口候选2秒；客户端未确认预测最多1秒，达到上界停止推进并显示恢复状态。2秒和1秒属于可调工程参数，须在实现后的延迟/成本验证中复核，不是用户额外批准的玩法限制。

已激活房间的active/combat场景即使无按键也提交有界空输入以推进AI/残留；有效输入可承担连接保活，不要求另发重复心跳事务。尚未enterRoom的加载阶段只按租约/加载握手管理，不提前启用2秒战斗输入缺口。completed/looting不要求每500ms模拟战斗，只按租约保持拾取场景；没有拾取倒计时。

服务端不确认未来逻辑时刻，累计接受前沿不得超过当前锚点可解释的墙钟活动时间；不能每段追加容差。连续输入超过候选缺口，先使场景进入有效恢复状态，停止新片段提交，返回RECOVERY_REQUIRED与最后确认前沿；截止沿原leaseUntil。心跳可以证明连接，但不能把未提交模拟的空白补成战斗，也不延长已开始的recovery。

客户端和服务端都不以“最后确认到恢复之间经过几秒”直接补模拟。恢复产生新时间段，anchorTick=原acceptedTick、anchorWallAt=服务端恢复时刻，排除未确认间隙。未确认片段最多一次在途；批量大小、动作数量和精度上界仍需内容/事务合同补齐。

### 6.3 恢复栅栏与在途写

1. 客户端停止预测与新业务写，查询在途原operation；notFound不等于原请求不可能随后提交。
2. 同一launch/session/rolePlayEpoch下提交幂等resumePrepare控制意图。事务内读取当前检查点、场景、租约和全部适用截止，并与旧输入提交争用同一检查点/挑战版本。
3. 旧片段先提交：恢复读到其最新状态及资产，不能回滚；resumePrepare先提交：递增timelineEpoch与检查点revision，旧锚点下尚未提交的片段拒绝，无消费/收益。
4. 返回冻结确认前沿、ready票据及版本化恢复视图；此时不connected、不建立活动锚点。完整状态/资源就绪后scene.ready才建立新锚点。短恢复不改rolePlayEpoch、sceneEpoch、roomToken或dropId，不重抽紫名/奖励，不清CD或复活；旧原结果仍可授权查询，但不能覆盖更新的读模型。
5. resumePrepare或ready响应丢失，按控制序号/票据查询原控制回执，不重复递增或刷新锚点。只有ready成功后的新有效连接阶段才更新leaseUntil，准备期间保留原恢复/死亡截止。

暂停与resume均是版本化控制事件，不是普通玩家按键；不为减少回溯增加持久输入收据体系，也不新增断线补偿/免费复活/离线续关。该方案不能证明真实物理断线瞬间或识别故意断线原因，反复暂停辅助操作仍需风控观察；不擅自增加恢复次数限制或惩罚。

### 6.4 截止边界与拒绝矩阵

所有允许继续的判断均要求serverNow严格小于适用截止；等于即到期。事务重试重新读取serverNow。原operation已提交时先返回原结果，不把响应迟到改成“未执行”；新的写不能凭客户端产生时间越过截止。

| 场景 | 候选权威结果 |
| --- | --- |
| 最后连接证据0秒、租约10秒；首次到期查询10秒 | active失败/关闭；不能再给到20秒；completed仅关闭拾取 |
| 0秒确认后静默，3秒发现输入缺口、原租约10秒 | 恢复截止仍10秒；resume成功时重建锚点，不补0至3秒战斗 |
| 死亡节点映射0.3秒、0.75秒提交确认 | deathDeadline=10.3秒，不是10.75秒 |
| 上述死亡后1秒显式暂停 | recoveryUntil=11秒，但死亡截止仍10.3秒；恢复必须同时早于两者 |
| 10.2秒恢复上述dead场景 | 若其他条件合法则仍dead，仅恢复连接；不会免费复活或重给死亡窗口 |
| 正好10.3秒请求复活/恢复 | 按死亡到期关闭active，不扣纹章；原已确认通关不能降失败 |
| 同一步死亡与最终Boss击杀 | 沿领域规则先记录死亡再认定通关及免费复活；顺序来自内核，不信任客户端自排事实 |
| 武器途中归零 | 不暂停、不改锚点/期限；继续本局，武器属性失效，新挑战前修理 |
| 恢复后旧输入到达 | 已提交原结果只读返回；未提交旧timelineEpoch拒绝，不能再扣药或发奖 |

此表是设计推演，不是已执行测试。加载/切房握手、同帧精度/舍入、资产动作上界和物理写预算继续分别收敛；加载CD推进的历史空白由2026-10-22用户同意的2A覆盖，见加载握手合同新增章节。正式eng-review必须先经用户确认启动，当前仅补方案。


2026-10-22评审决定2A：正常联网转场的角色CD/buff/既有自然回复继续计时，recovery段排除；transitionClock与恢复边界同笔保存，不以恢复重建锚点清除或重复计入已累计转场时间。详见[加载握手](room-loading-handshake-v1.md)，死亡/恢复10秒墙钟截止不变。


## 2026-10-22批准4A：恢复准备与就绪分开

scene.resumePrepare固定确认前沿与公开摘要，分页/资源准备期间仍recovery；scene.ready核对票据、revision/hash及全部原截止后才connected。不得提前启动2秒输入缺口或以准备/心跳延长10秒。ready成功丢响应读取同票据状态不重置锚点。新房awaitingReady采用同机制；正常联网角色转场计时依2A继续，真实recovery排除。本文历史“resume直接connected”语句由该两步协议替代，具体字段/失败路径见[批准合同](../reviews/eng-review-approved-contracts-2026-10-22.md)4A。


## FR02闭环：首次输入与时间段缺口

scene.ready首次成功且进入active/combat时，同笔设置inputGapBaseAt=serverNow；保留历史lastAcceptedInputAt、acceptedSeq/Tick，不伪造输入。新片段先验代次及serverNow−inputGapBaseAt；差值≥2000ms进入recovery并拒绝新执行，差值<2000ms才继续验证；成功接受新输入后同时更新inputGapBaseAt与lastAcceptedInputAt。心跳、旧operation和ready重放都不更新inputGapBaseAt。awaitingReady/转场加载与completed/looting不适用该缺口判断。每个活动时间段ready只初始化一次，重放不得换锚点续命。

例：0秒最后旧输入，3秒ready，新输入4.9秒可进入校验，5秒/5.1秒按缺口到期恢复；服务器不因旧lastAcceptedInputAt=0立即判超时。原死亡/恢复墙钟截止优先检查，ready不能越过截止；新恢复的固定租约仍沿既有规则。
