## 2. 动作原型（当前）

`client/` 已有固定房间、占位战士、虚拟摇杆、四阶段普攻、单怪/三怪近战对抗和扩散圆弧剑气。v0.6 Web Mobile H5 已构建，用户确认手机浏览器可以打开并操作；但人物与动作表现较差，尚未通过手感验收，剑气穿透和技能反馈也需专项验证。

目标是回答「移动、攻击、受击、技能在手机上是否好读且好玩」。动作原型规格和最小 Cocos 工程已建立；下一步先做一名战士的动作美术小样，集成后复评，再完成微信小游戏构建与性能验收。

已确认范围见[动作原型规格](action-prototype.md)：一个双刀战士、一固定镜头房间、一种近战怪（单怪/三怪）、四阶段普攻（约 300ms 衔接初值）、范围斩、无无敌突进和扩散圆弧剑气，以及血蓝、冷却、受击反馈和一键重试。验证有限纵深、朝向、Y 排序、连段中断重启、剑气扩散命中、技能前摇、击退、房间清场与非战斗恢复。

不接入拍卖、完整装备库或所有副本。原型不要求具备正式经济与永久资产，也不等同于离线 MVP。

已确认 Cocos Creator 3.8.8 + TypeScript、Note20 Ultra 首台真机、60 FPS 目标、横屏 480×270 基础战斗画布及摇杆两轴规则。右侧布局随追加技能更新为一个普攻和三个技能按钮，需复查触达与遮挡。当前样板源码具备摇杆、普攻、近战敌人和扩散剑气；首轮手机 H5 操作已通，但正式动画素材、剑气多怪命中、微信小游戏构建和更多设备覆盖仍待完成。

出口：通过动作原型规格中的验收场景，目标设备可玩，基本手感经用户确认，资源样板导出和加载成功，暴露的问题可指导下一阶段。本轮帧率目标已定；包体与启动时间先测量记录，尚无已确认数值上限，正式发布门槛另定。

## 3. 在线基础闭环

先用最小内容跑通「真实登录 → 创建角色 → 一次挑战 → 领取奖励 → 更换装备 → 重进游戏恢复」。

包括身份、会话、服务端资产、挑战和奖励记录、持久幂等、初始背包、装等/绑定、基础伤害与掉落；使用有限内容验证端到端协议。CloudBase 测试环境建设需另行明确资源操作范围。

出口：断网、响应丢失、重复请求、满包奖励和旧会话操作有明确结果；资产无重复或越权。客户端战斗验证能力和内测限制明确。

## 4. MVP — 升级与刷装体验

最终 MVP 包含：

- 战士与猎人，各 4 个职业主动技能，加种族被动和饰品主动。
- 1–30 级成长、统一属性/伤害规则、职业武器和 13 装备槽。
- 三个副本、已定难度结构、账号共享解锁、逐房怪物和奖励。
- 背包/拾取、20 个堆叠、背包商人、药品、出售/分解、100 格金库、待领奖励。
- 五品质与装等资格、绑定、两套紫装、传说散件、武器与耳环强化。
- 角色体力、账号钱包和基础商店/兑换。
- 服务端存档、断网恢复和当前装备评分排行榜。

建议分为「可升级通关」和「满级装备成长」两次内测交付，不同时铺满所有模板。完整 MVP 仍覆盖上述范围，任何删减需用户明确调整。

出口：通过 [MVP 验收标准](spec.md#13-mvp-验收标准)，完成一次新角色到满级及满级刷装体验，验证成长、经济和真机表现。闭测清档方案在执行前告知和确认。

## 5. 后续版本

### 拍卖行

前置：可靠掉落、背包、绑定、存档、钱包、资产流水，以及较强物品来源校验。随后设计资格、手续费、托管、购买、撤单、到期、交付和恢复；通过竞购/撤单、重试、越权和非法来源等场景验证后再开放。

### 内容与外观

扩充服装、装备模板、特殊效果、怪物和副本；基于已有数值骨架制作。点券商店扩展与活动另行设计。本期不接入充值。

### 远期

智力职业与法杖；好友社交。好友本期只预留，无页面、协议或玩法设计。无实时玩家联机战斗计划。

## 6. 模块设计顺序

| 顺序 | 设计输出 | 应先解决的问题 |
| --- | --- | --- |
| 1 | 动作原型规格 | 设备、操作、视角、资源和验收阈值 |
| 2 | 战斗/技能/数值规格 | 成长、公式、上限、技能、动作与状态 |
| 3 | 副本/怪物/奖励规格 | 区间、装等池、难度、流程、掉落和体力 |
| 4 | 装备/道具/背包规格 | 模板、绑定、套装、强化、容量与物品流转 |
| 5 | 身份/资产/在线协议规格 | 权限、事务、幂等、会话和断网恢复 |
| 6 | 排行榜/经济规格 | 当前评分、刷新、钱包、兑换和商店 |
| 7 | 拍卖规格（后续） | 来源安全、托管、竞态和交付 |

此表是细化顺序，不要求写完第 4 步才考虑资产模型。身份、资产与挑战边界需贯穿前面各模块，避免先做出客户端权威经济再返工。

每份模块规格应写明用户故事、状态/边界、验收场景、未定事项与实际依赖；准备实现时才拆成交付任务。任务按可验收结果划分，例如「通关后奖励可恢复」，不单纯按前端/后端分割。
