# 玩家搜索、检视与社交交互提案 v1

日期：2026-10-20。状态：后续功能规则储备，不纳入本期工作、开发或验收，非已完成开发；依据[当前规格](../spec.md)、[UI稿](ui-layout-specification-v1.md)及[UI审阅](../reviews/ui-design-review-v1.md)。未确认建议不作为编码依据。

## 已确认边界

- 检视入口为排行榜和角色名搜索，不采用城镇点击模型入口。
- 默认公开13槽穿戴装备、强化词条、套装、最终战斗属性及基本角色资料；不公开钱包、背包、金库、邮件、内部账号标识或资产审计来源。他人模式只读。
- 仅按角色名搜索，角色名不重复；创建时检查，原子占名防同名并发，已有共同对象另有乐观版本校验。占名与创建及初始化奖励原子提交，重试不重复创建。
- 社交规则已认可，但用户最新明确不在本期工作范围；玩家搜索/他人检视、好友、私聊及城镇其他玩家展示按后续功能管理，不据此引入多人协同战斗。

## 已确认：好友关系作为私聊入口权限

2026-10-20用户确认：采用双方确认的好友关系，检视页申请，目标接受后建立关系；双方成为好友后才可私聊。陌生人仍可搜索、检视和申请好友，私聊入口提示“成为好友后可私聊”。发送时服务端校验当前好友关系，不仅依赖客户端按钮状态。拉黑功能的具体政策仍待确认。

不允许陌生人直接发送私聊。用户已确认好友关系按账号共享：通过角色名查找并申请，切换战士或猎人保留好友关系；对方可看到当前使用的角色，但不自动获取该账号全部角色列表。关系移除后的消息处理尚待确认。

## 状态设计建议（尚未确认）

| 对象 | 状态与界面行为建议 |
| --- | --- |
| 好友申请 | 未申请、提交中、已申请待处理、已是好友、失败可重试；重复原请求返回同一结果，不形成重复申请 |
| 收到申请 | 接受或拒绝；接受与关系建立一致，旧页面操作后刷新实际关系 |
| 关系移除/拉黑 | 影响后续发消息权限；即使聊天窗口已打开，发送时服务端仍检查当前关系，不能只依赖按钮灰显 |
| 私聊发送 | 发送中、服务端已接受、明确失败、结果未知；服务端接受不表示对方在线或已读，未知结果查询/原消息重试不得重复投递 |
| 查询页面 | 未搜索、加载中、无结果、失败可重试、目标不存在；只返回公开投影，输入不直接决定可访问的私人资产 |

好友关系按账号共享已确认。私聊仅双方在线时可发送已确认，不提供离线留言。在线期间消息历史、未读同步、拉黑具体效果及容量/频控尚未确定。本表用于发现需要的状态，不替用户确认这些产品政策。

## 后续评审顺序

本轮停止扩展社交细节访谈，保留在线消息状态、拉黑、历史、搜索匹配等未决项至后续专题。社交完整方案不是本期工程评审前置条件；本期UI不得出现未实现的可操作社交入口，API不开放社交查询或发送。角色创建名称唯一与原子防重作为基础规则继续设计，名称规范化仍需在创建功能落地前收敛。后续启动社交时另补模块、DTO与验收。

## 账号共享关系的工程边界

以下为已确认规则的工程设计输入，具体字段与事务仍待eng-review：好友关系由两个账号标识关联，账号标识仅在服务端使用，对客户端提供受控的不透明社交引用；角色名用于查找、展示及记录申请时的目标角色，不充当好友关系主键。换角色不会重复建好友关系或将同一账号显示成多个好友。检视仍针对用户选择的角色，不因账号好友关系开放该账号所有角色或私人资产查询。当前角色与在线状态仅作为展示，状态时效、离线展示及刷新策略待后续定义，不扩展为高频轮询。

## 已确认：仅在线私聊

用户确认仅双方在线时可以私聊，不采用离线留言及下次上线补收方案。好友关系仍按账号共享；发送前服务端校验双方当前有效在线会话及好友关系，切换角色不要求重新加好友。客户端在线标记仅供展示，不作为发送权限依据；离线目标不能被客户端旧在线状态绕过。

发送中、服务端已接受、明确失败、结果未知需区分；请求超时不能直接宣称未发送，原消息重试防重复。在线状态的租约/心跳与断线判定阈值为工程待验证项，不能据“在线”承诺绝对实时。

边界待确认：发送校验时双方在线，但投递确认前对方断线，是否直接终止投递；在线聊天历史是否保留及是否跨重登可查看。不得将发送结果恢复查询变成离线留言或未确认的跨登录补收。
