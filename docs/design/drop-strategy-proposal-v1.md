# 掉落策略与动态配置方案 v1

2026-10-19。来源：用户明确要求掉落做成动态加载策略，测试可快速补缺，正式可调整收集节奏。策略化方向已确认，以下接口/加载时点是待实现设计。未修改业务代码、创建云资源或部署。

## 策略与配置分开

掉落入口统一：先校验奖励来源、职业、装等/品质及套装资格，再由策略选择合法装备，最后生成实例并持久化。套装只能来自30级特殊副本的硬规则不能被某份权重表绕过。

| 策略 | 行为 | 当前用途 |
| --- | --- | --- |
| weighted-random | 按合法池与配置权重随机，允许重复部位 | 怪物随机掉落；正式候选，正式概率未确认 |
| missing-slot-first | 检测穿戴/背包及有效待领/邮件，优先缺少部位，全齐回指定随机策略 | 已确认测试期特殊副本通关奖励 |
| 保底/缺件加权扩展 | 达到条件后补缺或逐步提高缺件权重 | 仅预留扩展方向，未确认、不宣称已实现 |

不在业务分支中写死“所有通关补缺件”。同一策略实现可以按环境、副本、难度、奖励来源使用不同配置；测试通关策略不自动影响随机怪物掉落。以后增加一种算法需实现并验证，但已有策略的选择、权重、概率和参数可通过配置发布调整，不要求每次重建客户端。

## 推荐配置结构

配置至少包含profileId、不可变version、schemaVersion、hash、允许环境/来源、副本与难度、strategyId及参数、合法模板池与权重、套装概率、全齐回退策略。测试配置绑定测试环境/授权测试账号；正式绑定独立profile，不能由客户端传一个test=true切换。

测试profile：特殊副本通关使用missing-slot-first并套装概率100%，通关装备仍一件；怪物使用随机profile。正式profile：套装概率、随机/加权/保底策略和收集目标待经济方案确认，不因为可以配置就默认上线测试补缺或某个正式概率。

加载的是经过校验的配置数据，strategyId从服务端已支持的策略注册表解析，不下载执行任意脚本。这样既能动态改策略选择，也能保持可测试、可回溯的算法版本。

## 加载、生效与回滚

建议服务端发布新不可变版本后，原子切换profile的activeVersion；后续新挑战读取该版本，客户端展示所需公开内容即可，不掌握最终抽奖权。配置发布与环境建设是后续工作，本轮没有实际配置服务或云端。

建议在创建挑战时固定该挑战的掉落版本/策略集合，记录可恢复引用或完整快照；进行中的挑战仍用旧版本，下一次挑战才采用新版本，避免同一挑战前后规则不同。缺件查询仍在实际生成奖励的资产事务中读取当前持有，不把开局背包冻结为整场真相。

已生成的奖励实例、待领及邮件不因热更新重新抽取；重试返回原结果。回滚只将activeVersion指回合法旧版本，旧版本不得删除到影响未结束挑战或审计。若新配置非法，发布拒绝/保持旧版本；已有挑战必须能用其固化配置结算，不能用重抽替代恢复。

## 预算、缺件与边界

配置校验：策略存在、权重非负且有合法候选、总概率/归一化定义明确、职业/装等/套装资格有效、最大产出和事务预算可接受、full-set回退不会递归成空池。暂未确认的正式保底计数不能临时藏在配置里上线。

缺件策略沿[经济方案](economy-proposal-v1.md#9-测试收集节奏与缺件检测方向已确认未实现)：角色/套装/档位/部位为键，穿戴/背包/有效奖励共同判定；同批次暂占、结算幂等、资产并发冲突重试。选出装备后持久化结果，不因重新登录/策略切换改抽。发放角色不能由客户端伪造。

## 需要的验收

1. 相同业务结算重试仅发一次，profile更新后重试仍返回原实例。
2. 测试缺1部位时下一次合法通关补该部位，穿戴/背包/待领状态分别覆盖；全齐不拒发。
3. 正式profile允许重复或其他已审策略，绝不自动继承测试缺件优先。
4. 挑战中切换版本/回滚，旧挑战依旧版、新挑战依activeVersion；配置重启恢复后结果不改变。
5. 非法配置不可激活，老挑战可恢复结算；怪物和通关来源不会错用profile。
6. 玩家实际丢弃/出售、有效奖励到期、跨角色绑定及同批次选择均按持有规则处理；不拿“避免重复”承诺所有来源永久不重复。
