# World of 308 — 技术与内容蓝图（讨论稿）

> 状态：草案。用于区分已确认方向与待决策事项；不是完整游戏设计，也不代表已确定实现方案。

## 1. 已知方向

- 新游戏使用独立 Git 仓库 `World-of-308`；仓库当前许可证为 MIT。
- 引擎已选择 Cocos Creator；具体 Creator 版本仍待确定。
- 目标体验为 2.5D 像素风横版动作 RPG，借鉴类型体验，不复用其他作品的名称、角色、素材或具体表达。
- 战斗为单人模式，不做实时玩家联机。
- 规划范围包含：职业、攻击、防御、装备、消耗/功能/服装道具、怪物、技能、背包、拍卖行、副本、体力、数值系统。
- 需要服务器范围内的装备评分等排行榜；拍卖行若保留，也属于在线异步服务。
- 没有专职美术，希望评估 AI 生图辅助与人工整理/修图的工作流。

## 2. 尚未锁定的关键决定

以下内容在设计会话确认前不应固化到工程配置或代码中：

1. 首发目标是微信小游戏、Android/iOS 原生 App，还是先小游戏验证并保留原生发布路径。
2. Cocos Creator 的具体版本、首发设备性能档位及横屏/竖屏规则。
3. 2.5D 的具体表现：纯侧视横版加多层景深，还是允许角色沿屏幕纵深移动。
4. 首版职业、战斗循环、角色成长速度和 MVP 内容量。
5. 是否首版就包含拍卖行、体力、服装外观，以及这些系统的范围。
6. CloudBase 环境、小游戏 AppID、用户身份绑定和云存档冲突策略。
7. MIT 许可证是否适用于之后加入的游戏素材、音频和第三方内容；素材来源应分别记录授权信息。

## 3. 推荐的项目边界

初期可用一个 Git 仓库管理客户端、文档和云端接口代码，避免过早拆成多个仓库；但不要把 Cocos 客户端和云端权限逻辑混为一体。

建议结构（待目标平台与 CloudBase 部署方式确定后调整）：

```text
World-of-308/
├─ client/                 # Cocos Creator 工程
│  ├─ assets/              # 场景、Prefab、脚本、游戏内资源
│  ├─ settings/            # Creator 工程设置
│  └─ extensions/          # 必要的项目扩展
├─ backend/                # 排行榜/存档/拍卖行服务或云函数
├─ docs/                   # 玩法、架构、资源清单、ADR
├─ tools/                  # 资源处理、构建辅助脚本
├─ .gitignore
└─ README.md
```

Git 建议：跟踪可复现构建所需的源文件、Cocos 工程配置和经确认可使用的游戏资源；忽略构建输出、临时缓存和 IDE 生成目录。体积较大的源 PSD、音频或原始生成图可评估 Git LFS。不要把密钥、云端管理员凭证或个人身份资料放进仓库。

## 4. 技术分层

### 客户端（Cocos Creator）

- 输入与表现：触控摇杆/按键、角色控制、相机、场景、动画、特效、音效、UI。
- 本地玩法：碰撞、攻击判定、受击、技能冷却、怪物 AI、副本状态、掉落与结算。
- 单机数据：在明确离线需求后，设计本地存档和升级迁移；客户端数据本身不能作为可信排行榜或交易凭证。
- 通过单独的 API/CloudBase 适配层访问线上功能，不让战斗逻辑直接依赖具体数据库 SDK。

### 在线服务（仅服务确实需要的能力）

- 排行榜：接收经校验的玩家成绩，按规则读取排名；不公开暴露可任意写入的数据集合。
- 云存档：记录用户身份、角色版本和存档版本；定义多设备冲突时的合并/覆盖规则。
- 拍卖行：服务端维护物品所有权、挂单状态和虚拟货币；购买、撤单、扣款、发货应由服务端完成并防止重复请求。
- 身份：单一 AppID 的身份可以作为首版范围；若以后跨 AppID 共享账号，需要额外设计账号绑定，不能默认 OpenID 相同。

首版不需要为了单人战斗建立实时房间服务器。在线功能可以评估 CloudBase 云函数或独立 API；选型取决于实际登录、交易、部署和调试需求。

## 5. 12 个系统的依赖关系与建议顺序

数值规则是底层：职业、攻击、防御、技能、装备、怪物和副本都依赖它。建议先制定少量、可解释的核心属性，避免属性、装备词条和技能效果互相膨胀。

```text
核心数值与战斗规则
  ├─ 职业 → 攻击/防御/技能 → 角色操作与打击反馈
  ├─ 怪物 → 副本 → 掉落
  └─ 装备/道具 → 背包 → 成长与评分
                         ├─ 排行榜（在线提交/读取）
                         └─ 拍卖行（在线权威交易，依赖身份与物品所有权）
体力 → 副本进入节奏（是否需要，待验证）
服装 → 外观展示（是否改变属性，待决定）
```

拍卖行的工程复杂度显著高于普通排行榜，因为它涉及共享状态、物品归属、货币和并发交易。即使玩家不实时同屏，拍卖行也会让物品经济成为在线服务；建议先有可验证的掉落、背包、装备和服务端存档，再决定是否进入 MVP。

## 6. 美术资源生产流程

### 先定规格，再批量出图

在大量生成立绘前，先确定：摄像机视角、逻辑分辨率、像素密度/缩放方式、角色高度、调色板、轮廓规则、光源方向、背景层次、文件命名、动画帧尺寸和碰撞/武器挂点约定。

### 建议的资源顺序

1. 角色/职业概念立绘：用于确认职业气质、轮廓、服装和武器，不直接当作游戏动画。
2. 角色侧视设定与比例稿：确定左右朝向、武器挂点、装备覆盖方式和像素尺寸。
3. 样板角色动画：待机、移动、跳跃/落地、普攻、受击、死亡；技能按首版玩法增加。
4. 样板怪物与攻击反馈：移动、攻击、受击、死亡，以及命中闪烁/打击特效。
5. 一块可玩场景：背景景深层、地面/碰撞、平台/机关、入口出口和生成点。
6. 技能特效、武器/装备外观、物品图标、背包/装备/副本 UI、音效。
7. 样板在目标手机和 Cocos 真机运行环境中通过后，再扩展职业、怪物、关卡和道具。

### 游戏内格式

- 立绘、头像、道具图标、背景通常是静态 PNG 或引擎可处理的纹理资源。
- 逐帧动作通常使用 PNG 精灵图集/帧序列加引擎动画配置；分层骨骼动画是另一种方案。
- GIF 可以用于预览或文档，不建议作为可控的游戏角色动画交付格式。
- 动画资源需要统一帧画布、锚点、帧率、命名和碰撞/攻击数据；AI 生图结果通常仍需挑选、切图、对齐、清理像素和真机校验。

首个美术验证包应小而完整：一个角色的核心动作、一只普通怪、一个技能特效、一小块场景和最基本的战斗 UI。不要先生成几十张孤立立绘。

## 7. 资源包与平台策略

Cocos Creator 3.8 文档支持把资源组织为 Asset Bundle，并可按平台配置为本地资源、小游戏分包或远程资源包。微信小游戏代码包目前文档列出的约束为：总包不超过 20 MB、主包不超过 4 MB；超出首包的内容需要通过分包或远程资源设计处理。远程资源会带来首次下载、缓存、版本更新、弱网失败和域名配置等额外工作。

建议先将启动必需的代码、首屏和最小样板资源保持轻量；关卡/内容包按需加载。任何体积估算都应以真实资源样板构建为准，而非按立绘数量猜测。若最终选择原生 App，也应保留内容包版本和更新策略的设计，但不需要照搬小游戏的包体限制。

## 8. 分阶段验证路线

### 阶段 A：设计闭环

确定目标平台、首版职业与核心循环；写出首版“必须有/暂缓”清单和关键数值假设。

### 阶段 B：Cocos 技术样片

创建最小工程，用临时素材跑通触控移动、攻击判定、怪物受击/死亡、场景碰撞和结算；确认横竖屏策略、目标手机性能和构建链路。

### 阶段 C：美术管线验证

把样板角色/怪物/场景按约定规格导入，验证像素缩放、帧动画、特效、UI、资源包体和加载时间。只有样板达到可接受质量后再批量出图。

### 阶段 D：单机 MVP

优先验证一名角色、一张小副本、少量怪物、一个 Boss、基础攻击/技能/防御、掉落、背包和装备成长。体力、拍卖行及多职业是否进入首版由玩法验证决定。

### 阶段 E：在线功能

加入身份、云存档和装备评分排行榜；以服务端校验写入。拍卖行作为独立后续阶段，先完成服务端所有权、货币与并发一致性方案，再实现 UI。

### 阶段 F：发布候选验证

对目标平台做真机兼容、弱网/断网、缓存/升级、性能、资源加载失败、存档损坏和安全规则验证；按选定平台走对应测试与发布流程。

## 9. 主要风险

- 首版系统范围过大：12 个系统都做全，会推迟验证最核心的战斗乐趣。
- 美术先行导致返工：立绘没有尺寸、视角和动画规格，难以直接变成游戏资产。
- AI 资源不一致：角色细节和逐帧姿势可能漂移，需要风格规范与人工整理。
- 小游戏远程资源体验：下载量、弱网、缓存淘汰和更新策略影响首次进入与离线可用性。
- 排行榜作弊：不能信任客户端直接上报的装备评分；防护等级应按内测/公开运营区分。
- 拍卖行数据安全：购买、撤单和货币变化必须由服务端控制，并考虑重试、并发和重复请求。
- 许可证与素材来源：仓库当前为 MIT；第三方素材、字体、音效和生成式 AI 资源需记录来源与授权，不能默认全部都能按 MIT 发布。

## 10. 当前建议

此阶段先完成玩法范围与目标平台决策，再创建 Cocos 工程。之后优先做“可玩灰盒 + 样板美术资源 + 真机资源包测试”，用实测结果判断微信小游戏是否足够，而不是先把 12 个系统或全部美术资产铺开。
